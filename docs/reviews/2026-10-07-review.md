## R1 · P1 · 限帧过滤会完全丢掉最终画面

位置：[lib/video.mjs](../../lib/video.mjs)，118–125 行。

过滤顺序是 `mpdecimate → select`。新状态若在距上个保留帧不到 `1 / fps` 时出现，`mpdecimate` 先保留第一次新状态，随后 `select` 丢掉它；之后相同的新状态又全部被 `mpdecimate` 丢掉。画面即使保持很久也不会再进入 GIF。

实测：30 fps、2 秒视频，首帧为黑色，第 2 帧起变白并保持到结束。默认 `--fps 10 --crop off` 只抽出时间戳 `[0]`，输出始终是黑色。这个触发方式对应按钮快速切换、操作完成后画面立即静止等常见录屏。

建议：重新安排采样与去重，或保留待输出候选帧并在间隔到达/流结束时提交；回归验证短于 100 ms 的状态切换以及最后一帧。不能仅提高默认 fps 掩盖问题。

## R2 · P1 · 自动裁剪漏掉最开始两次变化

位置：[lib/video.mjs](../../lib/video.mjs)，87–95 行。

`cropdetect` 未设置 `skip`，本机 ffmpeg 的默认值为 2。此处输入已经是关键帧差分，再跳过前两帧会漏掉只在开头出现的运动区域。`reset=0` 只累积后续检测到的范围，无法补回漏掉的区域。

实测：160×120 视频，开头左上区域发生变化，后半段右下区域发生变化。所有运动覆盖 `x=8..142, y=20..102`，`detectCrop` 却返回 `{x:110,y:70,w:32,h:32}`。完整 CLI 默认转换的 crop 为 `{x:108,y:68,w:36,h:36}`，开头的操作区域被裁掉。

建议：在差分管线上显式 `skip=0`，覆盖开头运动、只有少数关键帧以及全静止输入的回归用例。

## R3 · P2 · 迟到的旧录制回调会清掉新录制

位置：[native/Sources/Recorder.swift](../../native/Sources/Recorder.swift)，172–189 行；关联 [App.swift](../../native/Sources/App.swift)，172–176、239–246 行。

停止看门狗 30 秒后调用 `fail`，把 UI 设回 idle，但没有废弃旧 session。用户随后可以再次录制。delegate 回调既不检查 `recordingOutput` 身份，也没有 session id，而是直接读取共享的 `outURL` 并 `teardown()`。

验证：在临时副本中仅加入设置当前 output 的测试入口，令新 output/URL 成为当前 session，再调用旧 output 的 `recordingOutputDidFinishRecording`。实际 `onFinished` 收到 `/tmp/new-active.mov`，当前 output 被清空，`isRecording` 仍为 true。这个验证确认旧回调会误处理新 session；真实系统回调迟到的频率未测。

建议：每次录制分配 session id，delegate 只接收当前 output 的事件；超时后使旧 session 失效；teardown 同步重置所有状态。把这些状态变更统一隔离到同一执行上下文。

## R4 · P2 · 超过帧数上限时最后一帧必被舍弃

位置：[lib/video.mjs](../../lib/video.mjs)，132–137 行。

当 `N > cap` 时，最后索引为 `floor((cap - 1) * N / cap)`，小于 `N - 1`，无法保留最终状态。即使只多一帧也会丢结尾。

实测：红 → 绿 → 蓝三帧视频，用 `--max-frames 2` 转换只选择红、绿；原应停在蓝色的结果停在绿色。`241 → 240` 的索引检查最后为 239，丢掉索引 240。

建议：`cap >= 2` 时使用包含首尾的均匀采样；单帧上限需明确选择哪个状态。此问题独立于 R1，二者需分别修复。

## R5 · P2 · 子命令 stdout 破坏 JSON 输出协议

位置：[bin/screen2gif](../../bin/screen2gif)，292–300 行。

`--then` 使用 `stdio: 'inherit'`，所以子命令输出与最终 JSON 共享 stdout。README 推荐的 `record --then ... --json` 只在子命令完全不输出时才能被直接 JSON 解析。

模拟采集下执行 `--then 'printf CHILD_OUTPUT' --json`，stdout 实际以 `CHILD_OUTPUT{"ok":true,...}` 开头。`-q` 的“只输出路径”约定也有同类问题。

建议：在 `--json`/`-q` 模式把子命令 stdout 转到 stderr 或单独保存，stdout 只保留机器可读结果；普通模式继续透传。

## R6 · P2 · 系统支持声明和真实构建目标不一致

位置：[native/Info.plist](../../native/Info.plist)，19–20 行；[native/build.sh](../../native/build.sh)，29–37 行。

Info.plist 声明 macOS 14，代码无条件使用 macOS 15 才提供的 `SCRecordingOutput`。本机修补分支还把 deployment target 固定为 `arm64-apple-macosx26.2`，另一分支未显式设置最低系统目标。

证据：macOS 14 target 类型检查报 availability 错误；macOS 15 target 类型检查通过。当前产物 `otool -l` 显示 `minos 26.2`。因此该产物不能以“支持 macOS 14/15”交付。

建议：明确最低支持系统并统一 Info.plist、编译 target 和文档。若最低设为 15，应以 15 为 deployment target 构建并真机验收；若必须支持 14，需要另一套写文件实现。

## R7 · P2 · “已开始录制”的提示早于实际采集就绪

位置：[native/Sources/App.swift](../../native/Sources/App.swift)，183–205 行；关联 [RecordingOverlay.swift](../../native/Sources/RecordingOverlay.swift)，56–57、100–109、200–201 行。

状态条在 `recorder.start` 之前就显示 REC 并开始计时。框选的对焦动画独立运行，完成回调在 `.starting` 阶段也播放开始提示音。与此同时查询可录内容允许等待 60 秒，启动采集还可等待 10 秒。

当权限查询或系统采集启动变慢时，用户会听到开始提示、看到 REC，随后做出的操作却尚未被采集。`.starting` 阶段点“停止”也被 `stop()` 的 guard 忽略。这是静态代码路径结论，本轮没有人为制造慢授权来录屏验证。

建议：启动阶段显示“准备中”，实际写入开始后再启动 REC/计时和提示音；动画与采集准备都完成后才发就绪信号，并提供取消启动操作。

## R8 · P2 · 启动超时后的清理又进入无期限等待

位置：[native/Sources/Recorder.swift](../../native/Sources/Recorder.swift)，127–133 行。

`startCapture` 虽然被 10 秒超时包裹，catch 中却直接 `await stream.stopCapture()`，没有自己的期限。代码正在处理“系统采集回调不来”的情况，若停止回调也不来，外层 `start` 仍永远不会返回。GUI 留在 `.starting`，停止录制的 30 秒看门狗此时尚未启用。

建议：清理过程也有时间上限并作 session 失效处理；向 UI 报错不应依赖系统停止回调必然成功。保留必要引用，尽力后台清理，避免简单放弃系统采集会话。此项为静态异常路径发现，未诱发真实系统卡死。

## R9 · P2 · 每次框选都留下窗口引用环

位置：[native/Sources/RegionPicker.swift](../../native/Sources/RegionPicker.swift)，24–29 行。

`window` 强持有 `contentView`，`SelectionView` 强持有 `onPick`，该闭包又强捕获 `window`。选择完成或 Esc 取消只调用 `orderOut`，不会断开引用环。反复框选会不断留下窗口/视图资源。

建议：闭包弱捕获窗口，完成后清空回调/内容引用并保证只完成一次。这是 Swift 所有权关系的静态发现，本轮未做 Instruments 内存曲线验证。

## 其他限制和完善项

- app 不能作为独立应用随意移动：`Converter.cliURL()` 依赖 `<项目>/native/build/` 相对布局。代码已明确提示该限制，未把它计作新缺陷；若计划分发，应将 CLI 与 lib 打进 Resources。
- 应用缺少 `CFBundleIconFile` 和实际 icon 资源；菜单栏使用系统 `record.circle`。本次三款图只是候选，需要选定后制作 `.icns` 和单色菜单栏模板。
- `normalizeCrop` 用同一 `even` 处理坐标和尺寸，使零坐标变为 2；例如 `{x:0,y:0,w:160,h:40}` 会变成 `{x:2,y:2,w:160,h:40}`。属于边界校正问题，建议拆开对齐函数并保证裁剪矩形在源画面内。
- `--ready-file` 的预检会短暂创建随后删除最终信号文件，存在被“只看文件是否存在”的等待方误读的窗口；当前一次 watcher 实验未捕捉到预检文件，不把它写成已实测故障。建议预检使用同目录的独立临时文件。
- JSON 的 `frames`/`gifDuration` 是逻辑关键帧和计划时长，并非编码后统计。普通样本报告 3 帧/3.20 秒，ffprobe 实际为 4 帧/3.24 秒，来自尾帧重复及时间基量化。建议区分字段语义或探测成品后报告。
- 缺少可持续回归验证。建议先把 R1/R2/R4 的合成视频、R5 的 stdout 协议，以及 session 失效路径变成自动化测试。截图/文档声明不能替代这些检查。
